# Boards

## Templates

`otea init --template <key>`, `otea board add <name> --template <key>` and Studio's **Nuevo tablero** take the same templates: the starter catalogue below: eight single boards and the sets `ideas` and `repos`, which make several boards at once (below). `otea init --help` and `otea board add --help` list them from the same catalog. `otea board add <name> --template repos` makes every board of the set, the name (and `--item`) naming the first; its `--json` is the list of boards it published.

- A project starts with no board: `otea init` makes one only when `--template` names it (`none` makes none either), and the person picks the rest in Studio's **Nuevo tablero** or with `otea board add`. The empty project page offers **Elegir tableros** until the project has one.
- Every project also has **Pedidos**, the built-in board for loose requests, where an agent's board draft arrives. It is made when the project is first opened, but the places (the sidebar, `GET /api/collections`) list it only once it holds an item.
- `otea init --template` makes boards only on a project with no boards of its own (Pedidos aside). On a project that already has boards it makes none and, when given `--template`, says to add one with `otea board add`. An unknown template fails with exit 3 (`not_found`) either way.

## Collections from before boards

Projects made before boards kept each collection on a preset (`presets/<name>/preset.yaml`, official or the project's own). The first time such a project opens, every collection is read once as a board: an official preset becomes its template's board (`tasks` Tareas, `bug-triage` Errores, `change` Cambios plus Tareas de repo, and so on) with its own words for agents, and a project's own preset becomes a board of one step, Hacerlo, that keeps its items' fields, with the text of its playbooks (its own `playbook.md`, then its types') as the board's words, which agents read with `otea board <name>`. Nothing makes a collection on a preset any more: boards are made with `otea board add` or in Studio.

**Icons.** `otea init --icon <icon>` gives the project an icon, also on a project that already exists; a project without one is drawn as a two-letter monogram of its name. `otea collection icon <name> <icon>` gives a board its own icon in the lists (`otea collection icon <name> default` shows its default again). Icons are named as in [`src/core/icons.ts`](../src/core/icons.ts) (112 of them), and an unknown name fails with exit 6 (`invalid_icon`), naming the close ones, and changes nothing. `GET /api/collections` gives each collection its resolved `icon`, and `GET /api/project` the project's `id`, `name` and `icon` (`null` when it has none).

The starter catalogue: eleven generic boards named by what they manage, each a base to adapt to your own fields and steps in Studio (or to have an agent design one for your project, below). Between them they use every kind of evidence the item page shows: diffs, test reports, logs, Markdown and other files, diagrams, images (gallery, single, before and after), video and audio.

- **Pendientes** (`todos`): anything you hand an agent that is not code: writing, planning, organising, looking something up. One step, Hacerlo: the agent says what it did in plain words, with the images, files or links it made, and you approve it or send it back. No branch, no diff, no tests.
- **Errores** (`bug-reports`): bugs you find or the people who use what you make report. Completar (skipped when the report is complete), Triar (yours), Arreglar on its own branch, with the proof its kind asks for (a failing test for behaviour, a measurement for performance, a recording for a visual bug), which you review, and Integrar.
- **Cambios** (`changes`): the small changes you ask an agent for in your own project. Aclarar (skipped when you already said how you will check it) asks you what is unclear and writes the checks; Hacerlo is done on its own branch with its diff, and screenshots for a visual interface change, the terminal output for a command-line one or the test output for a bug, and you review it; Integrar is the land step: once you approve, the agent rebases, fast-forwards `main`, writes the commit and deletes the branch if its harness lets it, with no second approval; a rebase that conflicts goes back to Hacerlo with its reason (`otea handoff <id> --way Hacerlo --reason …`), where the resolution is reviewed. Otea guards the branch and `main`, which takes the branch only during Integrar.
- **Código en main** (`mainline`): the same changes for a project you keep on `main` with no branches, where nothing reaches the remote before you see it. The agent commits on `main` without pushing and hands it in with the diff of what is not pushed yet; once you approve, Subir pushes `main`. Otea refuses a push of `main` until then, and lets through only the `main` you approved.
- **Investigación** (`research`): a question searched with sources, answered in a recommendation you review; it never makes the change.
- **Decisiones** (`decisions`): research before deciding. The agent lays out options with sources, you decide, and it records an ADR when the repository keeps them.
- **Contenido** (`content`): posts, newsletters, docs pages, episodes. You approve the outline and the draft; the agent publishes what you approved.
- **Diseño visual** (`design`): anything judged by looking (interfaces, illustrations, sprites, generated images). An agent creates it and you review each round, marking on the images what to change and sending it back as many times as needed; each round is framed like the one before so you can compare them, and a blind A/B comparison is a choice made when the piece is created. A piece in the repository is made on a branch whose diff is asked once, not every round; one that lives on its own (an illustration, a generated image) asks for neither. Integrar lands it once you approve.
- **Experimentos** (`experiments`): a hypothesis, a plan with a baseline and one deciding metric, and a run you review. Nothing runs against live systems.
- **Ideas → Tareas** (`ideas`) and **Entregas con PR** (`repos`) make two boards each (below).

The first Studio's boards (`tasks`, `bugs`, `blog`, `triage`, `review`) are retired: no list offers them, and projects made with them keep their boards. The earlier catalogue's `digest`, `assets`, `support`, `visual-iteration`, `playtest`, `resume` and `repobugs` are gone.

## The Matrix

The Matrix is a board view that weighs open items by two of their fields. **Ideas** and **Cambios** use effort × impact, and **Errores** uses effort × risk. These three boards have it from the start. In Studio, any board gets it once two of its fields play the effort, risk or impact roles (`analysis` in `board.json`).

- **The scales.** Effort is a size (Pequeño, Mediano, Grande, Enorme).
- **The quadrants.** A corner names each one:
  - on effort × impact: Victorias rápidas, Grandes apuestas, Para un rato libre, Pozos de tiempo;
  - on effort × risk: Rápidas y seguras, Rápidas pero delicadas, Largas pero seguras, Largas y delicadas.
- **Agents estimate the two values.** `otea next` asks an agent for them under **Estimate**, and the Matrix marks an agent's value as estimated until you set it yourself.
- **You order the work.** Pick items there and use **Fijar el orden** or **Poner arriba**.
  - `otea next` offers them in that order and says why ("It is number 1 in the order the person fixed on the Matrix").
  - `otea list` shows `on top 1` and `order 2` beside them, and its `--json` gives each such item's `priority`.
  - A step you do or review yourself still waits for you in Te toca: the order only changes what agents take first.
- **Approved items land in that order, one at a time.** On a land step (Integrar, or whatever a board calls the step where an agent merges what you approved), one agent lands at a time in each base branch (per repo), and the next to land is the approved item highest in your order: on top first, then your order, then the one approved first.
  - `otea next` offers only that item, and says what an item waits for while another lands.
  - `otea claim` refuses the others, saying which item lands first and why, for example `CAM-6 lands in main first (order 1), then CAM-5`.
  - An item whose question waits for you never holds up the ones after it.
  - You still decide: reorder the Matrix or put an item on top to change what lands next, move an item by hand, or leave one for an agent with Reasignar, which then lands it when it takes it.

## Templates that make several boards

A template set makes several boards at once, joined the only way boards are declared to join: **"se divide en"** (each item of one board divides into items of another).

```sh
otea init --template ideas     # Ideas, each divided into its Decisions, and Implementación, the tasks a planned Idea makes
otea init --template repos     # Trabajos, which divides into Entregas (always: a delivery is always part of a Trabajo)
```

- **Ideas → Tareas** (`ideas`): an agent refines each Idea by asking you, one question at a time, into a Brief (or a Decision into its Options), designs it (an architecture document, Mermaid diagrams, the project's `.md` files) once its Decisions, parts on the same board, are closed, and plans it: it creates the tasks on Implementación, each linked `implements` to the Idea and `blocks` in order. Those tasks wait until you approve the plan. A task born complete skips Preparar; Hacer waits for its subtasks and blockers, and is done on the task's own Rama, which Integrar lands on main once you approve it (as on Cambios), so an approval never closes a task whose code lives only on an agent's branch.
- **Entregas con PR** (`repos`): a Trabajo is born from a GitHub issue; an agent analyses it into a plan with one line per delivery and a merge plan, which you approve, then creates one Entrega per line (`--parent`), linked `blocks` in merge order. Each Entrega is done on its own branch by one agent and reviewed by another; you approve its merge once its blockers are in (Aprobar el merge), and Otea guards both its branch and `main`. Once the Entregas are merged, the Trabajo's agent tests everything together and hands it off. Record a merge with `otea merged <id> --pr <url>`; when a Done Entrega's PR conflicts before it is merged, `otea reopen <id> --reason "…"` takes it back to Implementar and through review again.
- A part on a board that is always part of another needs `--parent` (`otea create --collection Entregas --parent TRA-1 …`); without it, or with a parent on another board, the create fails with exit 16 (`parent_required`, `parent_type`). `otea link A parent B` follows the same rule.
- Every other link (`blocks`, `implements`, `relates`, `duplicates`) is free between any two boards. A step that waits for its blockers ("Algo que esperar") is not handed off, or approved, while one of them is open (exit 4, `blockers_open`); one that waits for its parts, while a part is open (exit 4, `children_open`).
- Blueprints are gone. A project that had one is read once, when it opens: every collection becomes a board (each old preset has its own reading, so a `change` collection becomes Cambios plus Tareas de repo and its repo tasks move there with their history), a `blocks` connection into a board makes its working step wait for blockers, and `.otea/blueprint.yaml` is deleted once every collection reads as a board (while one cannot be read yet, Otea warns and keeps it). A collection on a preset Otea never shipped keeps its git gates as a guard on its `branch` field.

## An agent drafting a board

In Studio, **Que lo esboce un agente** (on Studio's home and in **Nuevo tablero**) leaves a board for an agent to draft: it waits as a draft, and a Pedido (assigned to the agent when one is named) keeps what the board is for in the person's words. How to hand it in is the instructions of the Pedido's step, which `otea next` and `otea show` give the agent; the Pedido's page links to the board in Studio.

An agent the person asks for a board starts the same thing from the CLI or MCP (the `board_draft` tool, with `new` and `why`): `otea board draft --new "<name>" --why "<what it is for>"` makes the waiting board and its Pedido, held by the agent, with `--why` as what the board is for. A name another board or draft has is refused (`already_exists`), as in Studio, and an unnamed agent too. With `--file board.json` it hands the draft in at once, checked as below; a file that is not a board makes nothing. It prints the Pedido and the board's link in Studio, where it waits for the person to try and publish: agents never publish.

`--template <key>` starts the draft from a board of the catalogue (one board, never a set) instead of a blank one, so the agent adapts the closest template rather than writing a board from nothing.

A change to a board already published (a field, a step) goes the same way: `otea board draft --change <board> --why "<what to change>"` makes a Pedido held by the agent, titled `Cambiar el tablero <board>`, and leaves the board's draft waiting on it. The draft starts from the one the person already has in Studio, or else from the board as published. The live board keeps working as it is. The agent hands its board.json in on the Pedido as above, and the person publishes the change in Studio, which closes the Pedido. While one change waits, a second is refused (`already_exists`) and names that Pedido.

```sh
otea board draft --new "Piezas" --why "The game's screens, reviewed by looking" --template design   # PED-1, starting from Diseño visual
otea board draft PED-1                                 # the draft to start from: every key a board takes
otea board draft PED-1 --file - < board.json           # check it as a board and hand it in on the Pedido, from stdin
```

- The Pedido's instructions hand the draft in on stdin (`--file -`, with the JSON piped in or in a here-document), so no `board.json` is left in the repo, and none is written outside the project either, where a harness asks the person's leave for every command that touches it. `--file <path>` still reads a file. A `board.json` with a UTF-8 BOM (PowerShell 5's `Out-File -Encoding utf8`) reads as any other.

- The shape of `board.json` is published as a JSON Schema, [`schemas/board.schema.json`](../schemas/board.schema.json), each key with what it is for and an example: check a draft against it before handing it in. It is generated from the board's zod schema (`src/core/board/schema.ts`), and a test keeps the two together.
- A file that is not a board is refused (exit 9, `invalid_board`) with one line per problem: where, in the board's terms (`step 2 "Fix" › handoff 1 (fsteps) › req`), what was expected and what it found, what the key is for with an example, and the JSON path (`[steps.1.hand.0.req]`). Then it points at the draft to start from, the schema, and Studio, where the person can finish what is hard to say in JSON.
- A board that is a board but not ready (a step with no name, an agent closing an item as Done) is handed in all the same, and the command lists what is still to fix for it to be published.
- A step is done by `"you"` (the person) or `"any"` agent, and reviewed by `"none"`, `"you"` or `"any"` agent; a step never names one agent. A board written before, whose step names one (`{"agent": "claude-b"}`), is read as `"any"`, nothing else changing: a hand-in says so under `Read as today's board:` (and `PUT /api/boards/:id/draft` answers it as `notes`), and a board already stored reads the same way.
- Publishing the board offers to close its Pedido as done (checked by default): publishing is the person taking the draft. Unchecked, the Pedido stays open.

## Archiving and deleting a board

A board you no longer work on is archived, or deleted, from its menu in Studio's editor (**Archivar tablero…**, **Eliminar tablero…**). Both are the person's acts, like publishing: there is no CLI or MCP command for them, and the API (`POST /api/boards/:id/archive`, `POST /api/boards/:id/unarchive`, `DELETE /api/boards/:id`) takes them only from this computer's signed-in browser, refusing a request without the session (an agent), one a proxy forwarded and a paired phone. Pedidos, the built-in board for requests, is never archived or deleted (`forbidden`, details `board_builtin`).

- **Archiving** takes the board out of every list: Te toca, Triage, the board views and filters, the phone, `otea next`, `otea list`, the index of `otea board` and the git gates. Its items stay to read, with their history and evidence, in Studio's **Archivados** (`GET /api/boards/archived`), where they are searched by title or id and opened read-only. Open items may be archived: they freeze where they stand, and the leases on them are released (each with a `released` event, cause `archive`); the confirmation says how many freeze and how many leases go. Nothing writes to an archived item: a move, an update, a claim, a heartbeat, a note, a question, a link, evidence or a new item on the board fails with exit 21 (`board_archived`, HTTP 409), saying the board is archived and the person restores it in Studio. Its name stays taken, and Studio does not change it while it is archived.
- **Restoring** (**Restaurar** in Archivados, or **Deshacer** in the toast) brings everything back as it was: the board in the lists, its items where they stood and writable again. Released leases are not taken again: an agent claims the item anew.
- **Deleting** takes a board without items at once, after one confirmation. A board with items is archived first, then deleted from Archivados once you type its name (the API refuses `{"confirm": "<name>"}` that does not match, `reason_required`, details `board_delete_confirm`): its items, their history, notes and evidence go for good, while an empty board loses nothing a template cannot make again. Deleting removes the board, its versions, its draft, its collection and its items with their events, evidence and links; an evidence file goes from the project's data folder unless another item's evidence shares it. Events on other items stay as they were written, a link to a deleted item included.
- **A board another divides into** (Entregas, under Trabajos) goes with its parent: archiving, restoring and deleting Trabajos takes Entregas along, as the confirmation says, and the child alone is refused while its parent stands (`in_use`, details `board_split_child`), since the parent's items have their parts there.

## Agent moves on a board

```sh
otea handoff BUG-4 --note "the test I ran and what I saw"   # a step that asks for a note refuses without it (exit 8)
otea handoff BUG-4 --way "Triar" --reason "Cannot reproduce"  # a way back: no review, Triar starts its next round
otea drop TAR-3 --reason "Out of scope" --motive "Duplicado" # drop with a motive (by name or id), where the board lets agents drop
otea check --gate push --branch --repo                     # reads the board's protected Rama and its repo field
```

- On a step any agent reviews, an agent never reviews a step it did in that round (handed it off or, while the step was being done, claimed the item, attached evidence or changed its fields): `otea next` never offers it that review (`You did this step in this round: another agent reviews it.`), and its `otea claim`, `otea approve`, `otea send-back` or `otea move` of the review exits 7 (`forbidden`, details `own_review`) or 4 (`not_claimable`). Another agent reviews it; work of an earlier round does not count.
- The note of each handoff is kept with its round (`otea show --json`: `board.notes`). A way back needs `--reason` (exit 2, `reason_required`).
- A round that a send-back started opens, in `otea next` and `otea show`, with `Sent back to you: "…"`: the reviewer's note, who sent it, when and from which review (`sentBack` in `otea next --json`, `board.sentBack` in `otea show --json`, and the same over MCP). `otea next` offers items sent back before the rest, and handing one in again needs `--note` saying what changed, even on a step that asks for no note (exit 8).
- While an agent does a step, the person can leave it a note (from the item's page, the phone included) without changing the step, the round or the lease, optionally on a piece of evidence already attached in this round: the note points at that very file, not at a later one attached in its place, and for a recording at the moment seen. Several notes may wait at once, numbered per item. The agent reads them in the answers it already asks for: `otea heartbeat` and `otea attach` add `New note from the person (note 3, unanswered): …` with the moment it was left in (the evidence it is on, the time, how many of the step's required handoff deliverables were in, the handoff note not counted) and the command that answers it; `otea next` and `otea show` list the round's notes under `Notes from the person`, and their Handoff gains `Notes from the person answered: required`. Over MCP and `--json` the same block comes as `text` (in `next`, in its text) and the notes as `notes`. `otea wait` wakes on a note waiting on an item the agent holds (`TAR-7: new note from the person (note 3). Read it: otea show TAR-7`).
- The agent answers with `otea reply TAR-7 --note 3 "<a short answer>"` (MCP `reply`, with `note` and `answer`); a handoff is refused while a note of the round is unanswered, as one missing a note is (exit 8, `missing_fields`), with the command that answers it. An agent never opens a thread itself: what it asks the person goes through `otea ask`, which changes the turn. Leaving a note and answering it are kept as `note_left` and `note_answered` events, the answer with the agent's name.
- To ask the person something while it does a step, the agent runs `otea ask TAR-7 "<the question>"` (MCP `ask`, with `question`). The turn is the person's until they answer, in Otea or in the chat: an answer they give in the chat the agent puts on the question in their words with `otea answer TAR-7 "<their words>"` (MCP `answer`), which `otea ask` names. It is kept as the person's answer, marked as noted by that agent (the item's history says «Respondido en el chat, anotado por …»), and it gives the turn back as an answer in Otea does. The step, the round and the lease stay as they are, and one question waits at a time. Meanwhile the item is under **Preguntas para ti** in Te toca, the agents column says the agent waits for your answer, and the item's page asks it with a box to answer it (the phone too); `otea next` offers the item to no agent, `otea next` and `otea show` say `Waiting for the person to answer your question: "…"`, and a handoff is refused (exit 4, `invalid_transition`). The person's answer gives the turn back to the agent in the same round: `otea wait` wakes on it (`TAR-7: the person answered your question. Read it: otea show TAR-7`), and `otea next` and `otea show` give `You asked the person: "…"` and `The person answered: "…"`, to address in the round as a send-back note. Until then the agent's `otea wait --turn agent` still wakes for a send-back of its other work, for work that reaches the agent turn after it asked, for an item it holds whose parts or blockers closed after it asked, and for the person's note or «Retomar» on agent work after it asked (until the agent acts on that item), but not for work already free when it asked. Meanwhile an item it holds says «claude-haiku lo tiene, pero espera tu respuesta en IDE-10» on the desk and the phone, not that the agent is doing it (the API gives such an item `holderAsks: { by, item }`). While a question waits, the list, `otea show --json` and the API give the item `turn: "human"` and `asks: { question, by, text, at }`, and its page's `board.questions` keeps every round's (`POST /api/items/:id/answer` with `{ "text" }` answers it). Asking and answering are kept as `question_asked` and `question_answered` events. A handoff whose words end in a question mark is no longer a question: only old events written before `otea ask` still read that way.
- `otea drop` without `--reason` or, on a board with motives, without `--motive` exits 2; where only the person drops it exits 7 (`forbidden`); where the person drops only from the page, a relayed drop exits 4.
- `otea check` and the pre-push hook (`otea hook install --git`) match the branch and the repo against the board's **Rama** field (the branch field Otea protects) and the field it names as the repo, never against a fixed `branch` key: a push is allowed only while one of the chosen steps is being done (frozen while it is reviewed), a merge once the item is Done. Repo names match whatever their case (`--repo API` is `api`), as git hosts and the file systems of Windows and macOS take them, so `otea repos add` refuses a name another repo already holds in any case.
- Once an item was handed off, the pre-push hook refuses a push that rewrites its branch on the remote instead of adding to it (a force push after a rebase or an amend), naming the item and the commit handed off: the branch holds what the review read, and another agent may have added to it. Before the first handoff a rewrite is the agent's own. While the item is landed, the push is held to what the person approved instead, so a rebase onto the base with the same result passes. An agent adds commits and merges the base in; the person rewrites it past the hook with `git push --force-with-lease --no-verify`.
- `otea show` of a repo task says whether the checkouts of its repo in the project's folders have the pre-push hook (`Git hook: installed in <path>`, or `not installed in <path>: run otea hook install --git there`); `--json` and the MCP `show` tool carry it as `gitHook: { repo, installed, missing }`, with the checkouts' paths. A push from a checkout without the hook is never checked.
- Without more, the base branch is not checked: with an item in review, an agent could merge its branch into `main` locally and push `main`. In Studio, under the protected **Rama**, **It protects the base branch too** names the base branch (`"guard": { "base": "main" }` in `board.json`). Then a push or a merge into it is allowed only when it brings in the branch of at least one of the board's items and every such item is Done: the pre-push hook passes `--commits <remote>..<local>` so `otea check` sees which local branches the push brings in (`git push origin feat/x:main`, a local merge then `git push`). A push straight onto the base, or of a branch still in review, is refused. So is a push of a branch no item names (P5-R3-2): where a board protects a base, a push in the project takes only the branch of an item, while its step allows it, or the base, under this rule; a branch no item names is no item's work, so the hook refuses it, deleting it included, and the refusal tells the agent to push its item's branch or set the branch on its item first. Boards that protect no base leave such a branch alone, as before. The person still can: merging on the repository's website, or `git push --no-verify` past the hook, which the refusal says to them in the board's language.
- Working straight on the base, with no branches: a board for that needs no protected **Rama** at all, and the agent drafting a board takes the guard off when the person says they work on main. To have each push of main wait for the person's approval instead, keep the **Rama** with `main` as its base and as the item's branch, pushed only in the step after the approval (Integrar). Then a push of `main` is checked against the open items whose branch is `main`, by their own step: refused while one is being done or reviewed, allowed while it is landed in Integrar.
- Integrar says what it does before it does it. Approving the step before it says, under the button, that an agent then merges the branch into the base and pushes the base to the remote. While the item is in Integrar, its branch line says an agent merges it into the base and pushes now. On a board with no land step, approving into Done says nothing is merged yet, and the board's row reads «Aprobado, sin fusionar» (Approved, not merged yet) until `otea merged` records it.
- While an agent lands an approved item in Integrar, the person can still send it back to the step they approved (Devolver, with a note), as from a review.
- A branch merged outside Otea (on the forge, or by hand) is noticed: when git shows the branch of an item in Integrar is in the base already, `otea show` and `otea next` say so first and tell the agent to fill in what Integrar asks and hand it off. For a Done item on a board with no land step, they say to record it with `otea merged`.
- On a board with a land step (Integrar), a refused merge says it is allowed once the person approved the item, while it is landed there, or once it is Done; not "only once it is Done".
- While a step that pushes the protected branch is reviewed, the branch is frozen and an agent's `otea attach` on the item is refused (exit 4), so the reviewer approves only what was handed off. It may attach again once the item is sent back.
- `otea hook install --forge` has the forge enforce the base branches the boards protect, whatever tool pushes or merges. With `gh` installed and signed in, it sets a GitHub ruleset named `Otea: protected base branches` on the repository checked out. The ruleset targets each protected base and refuses a direct push, a force push and a deletion; changes reach the base only through a pull request (no approvals required). Running it again replaces Otea's ruleset with the bases the boards protect now, and `otea hook remove --forge` deletes it, leaving every other ruleset. Without `gh`, signed out, with no GitHub remote, or when GitHub refuses (a private repository on a plan without rulesets, or no admin rights), it changes nothing, prints the exact steps to set the same ruleset by hand under Settings > Rules > Rulesets, and exits 22 (`forge_unavailable`). It never asks for a token: `gh` holds it. What the forge does not know is whether the item is approved. Merging a PR early is still caught by `otea check --gate merge`, which agents are told to run.
- Otea installs no harness hook: no gate depends on Claude Code, OpenCode or any other tool. The pre-push hook stops a push from any tool. `otea hook remove --claude` takes out the Claude Code hooks and allow rules an older `otea hook install --claude` wrote to `.claude/settings.local.json`; run it once in a repo that has them, since the command they call is gone and Claude Code would block every `git push` and `gh pr merge` on its usage error.

| `otea check` exit | Name | Meaning |
| --- | --- | --- |
| 0 | `ok` | allowed, or nothing gates the action, or the check could not run (fails open, with a note on stderr) |
| 19 | `gate_refused` | refused; the reason on stdout. The pre-push hook stops the push on this code only |
| 2 | `usage`, `invalid_gate` | a gate or a field no board declares (`--gate psuh`, `--gate deploy`): the message names the gates there are (`merge, push`) |
| 1 | `unexpected` | Otea failed; a hook lets the action go on |
